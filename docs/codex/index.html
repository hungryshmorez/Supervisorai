Overview

Autonomous agents fail in a specific, expensive way: they lose the plot. A coding agent starts fixing a bug and quietly drifts into rewriting unrelated files; a research assistant confidently cites a source that says the opposite of what it claims; a multi-step task reports “done” while a dependency silently failed. The missing piece is not a bigger worker model — it is a supervisor that holds the plan, checks every step against it, and refuses to declare success until the work actually verifies.

SupervisorAI is that supervisor. It uses MiniMax-M3’s reasoning to run a closed loop over a team of workers, and it grew into a full autonomous studio with a specialist roster, a continuity engine, on-disk deliverables, and a human-in-the-loop safety gate. Two command-line “skills” (VORTEX-OS and VORTEX-OS-v3) and a browser extension round out the platform.

The reasoning loop

M3 decomposes a goal into a validated task DAG, delegates each task to an M3-backed worker, then puts on its supervisor hat and audits every output against the plan — catching hallucinations, errors, and drift. Failed or drifted outputs are re-prompted with a concrete correction hint. Only when every dependency passes verification does the system synthesize a final, verified result.

The single integration point is src/llm/client.py (LLMClient). Every LLM-using component depends on it, so retargeting this one class flips the whole platform onto MiniMax-M3.

The five stages

1 · PlanM3 decomposes the goal into a validated task DAG with dependencies and assigns each task a specialist persona.
2 · DelegateEach ready task (from get_ready_tasks()) is dispatched to an M3-backed worker running with its persona as a system prompt.
3 · AuditEvery output is verified against the plan via an M3 audit verdict, a heuristic QualityAnalyzer, an LLMJudge second opinion, and a coherence/drift check.
4 · CorrectFailed or drifted outputs are re-prompted with a concrete correction hint and re-audited — the loop self-heals.
5 · SynthesisOnly when every dependency passes does the system produce a final, verified result.

Studio capabilities

On top of the reasoning loop, SupervisorAI runs as an autonomous studio.

🎭 Specialist agent roster

Named worker personas live in agents/*.json. M3 assigns the best specialist to each task during planning, and each worker runs with its persona as its system prompt.

🧵 Continuity engine

Pass continuity_rules (era, character, tone, safety canon) to run_goal; they are injected into every worker prompt, folded into each audit’s checks, and guarded by a fast deterministic pre-check. Violations trigger a self-healing correction.

📄 On-disk deliverables

Every verified worker output is written to deliverables/<file> with markdown-fence stripping, so .html/.py/.json are valid standalone files. A run produces real artifacts, not just text.

🛡️ Human-in-the-Loop (Deep-Sleep) gate

Tasks the planner marks high_stakes (finalizing/packaging a shippable artifact) halt before they are written and require explicit human approval via the hitl_status / hitl_approve / hitl_deny MCP tools.

Never auto-approved. The HITL gate is the last line of defense before a shippable artifact leaves the system.

The VORTEX-OS studio skills

The Python engine grew out of VORTEX-OS, a bash “skill” that runs the same 4-tier orchestration from the command line. Both flavors ship in the repo, and both call MiniMax-M3 on GMI Cloud for real (via lib/minimax.sh).

vortex-os/

The creative studio flavor. A 4-tier chain of command, HITL Deep-Sleep gate, continuity engine, self-healing, and real on-disk deliverables.

./skill.sh --dispatch-master objective.md
vortex-os-v3/

The software-engineering flavor. A 30+ agent roster with dynamic agents, consensus voting, cost governance, and quality gates, driven by adapters/minimax_m3.sh.

make test   ·   ./skill.sh

Set GMI_API_KEY and each skill runs against real M3; without a key both fall back to a deterministic offline mode so they never hard-crash.

Core modules

The platform is organized as a standard Python project under src/.

llm/The single LLM integration point — LLMClient with retry/backoff, token-budget accounting, robust JSON extraction, tool-calling, SSE streaming, and a graceful mock fallback.
orchestrator/The DAG orchestrator, task decomposer, specialist roster assignment, prompts, and the HITL gate.
supervisor_agent/SupervisorCore and the Expectimax decision agent (ALLOW / WARN / CORRECT / ESCALATE).
monitoring/Monitoring engine, resource monitor, and the QualityAnalyzer heuristics.
task_coherence/Drift and coherence checks that keep worker output aligned to the plan.
researcher/The proactive research assistant that detects a stuck agent and synthesizes a recovery suggestion.
reporting/Dashboards, alerts, and confidence reporting.
idea_validation/Idea validation utilities (feasibility, skills, market niche).
server/The MCP server (src/server/main.py) that exposes the supervisor as tools.
error_handling/Shared error-handling primitives used across the engine.

MiniMax-M3 / GMI Cloud integration

Endpointhttps://api.gmi-serving.com/v1/messages (Anthropic Messages-compatible)
Base URLhttps://api.gmi-serving.com/v1 (env GMI_BASE_URL)
ModelMiniMaxAI/MiniMax-M3 (env SUPERVISOR_MODEL)
Authx-api-key: $GMI_API_KEY and Authorization: Bearer $GMI_API_KEY (both sent)

LLMClient adds production concerns on top of the raw endpoint: retry with exponential backoff (on 429/5xx/network), token-budget accounting, robust structured-JSON extraction, tool-calling pass-through, SSE streaming, and a graceful mock fallback so the demo, tests, and MCP server never hard-crash when no key is set.

Security: never commit your GMI_API_KEY. It belongs in .env (gitignored) only. Rotate any key shared in plaintext.

Quickstart

# 1. Install
pip install -r requirements.txt

# 2. Configure your GMI key
cp .env.example .env      # then paste your GMI_API_KEY
#   (or:  export GMI_API_KEY="<your key>")

# 3. Run the turnkey demo — plan, delegate, audit, self-correct, verify
python demo.py

# 4. Run the test suite
PYTHONPATH=src pytest tests/ -q

# 5. (optional) Run the MCP server exposing the supervisor as tools
PYTHONPATH=src python src/server/main.py

With no GMI_API_KEY the demo still runs end-to-end on a deterministic mock, so you can see the loop before wiring a key.

Glossary

Task DAGA directed acyclic graph of tasks with explicit dependencies, produced by the planner.
DriftWhen a worker’s output diverges from the plan — off-task work, empty stubs, or unrelated changes. Caught by the coherence check.
Audit verdictThe supervisor’s pass/fail judgment of an output against the plan, with a confidence score.
Self-healA re-prompt of a failed/drifted task with a concrete correction hint, followed by a re-audit.
HITL / Deep-SleepThe human-in-the-loop gate that halts high_stakes tasks for explicit approval.
ExpectimaxThe probabilistic decision algorithm the supervisor uses to choose ALLOW / WARN / CORRECT / ESCALATE.
MCPModel Context Protocol — the interface the supervisor is exposed through as a set of tools.
